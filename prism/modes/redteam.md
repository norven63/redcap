# 红队模式（Red Team）

> 对抗性审查。主动寻找风险、漏洞和被忽视的问题。

---

## 适用场景
- 核心协议改动（CONTRIBUTING.md §1-§10、SKILL.md §5.x）提交前
- soul.md / identity.md 重大修改的风险评估
- 新角色/新触发规则引入前的安全审查
- 任何"感觉很顺但直觉有点不对"的改动

## 协议族
独立取样协议（见 `../protocol.md §一`）

## 特殊约束
**跨家族要求**：Agent 组合中至少 1 个来自不同模型家族（如 Claude 组 + GPT 组合）。
理由：同家族模型共享训练偏见，无法真正独立挑战同族模型的假设。

## 角色分配
每个 Agent 都被设定为"挑剔审查员"，但从不同维度攻击：

| 维度 | 关注点 |
|------|-------|
| 协议完整性 | 是否有边界条件、未定义行为、循环依赖 |
| 向后兼容 | 是否破坏现有工作流、触发条件是否冲突 |
| 认知负担 | 是否增加执行复杂度、文档是否清晰 |
| 极端场景 | 在最坏输入下会发生什么 |
| 遗漏项 | 哪些 should-have 被漏掉了 |

## 输出格式约束（在标准 Schema 基础上）
`blockers` 字段必须按严重程度分类：
```
"blockers": [
  "[BLOCKING] 具体问题",
  "[CRITICAL] 具体问题",
  "[MAJOR] 具体问题"
]
```

## 成功标准
- **Pass**：无 BLOCKING 项，CRITICAL 项 ≤1 且有明确修复路径
- **Conditional Pass**：有 CRITICAL 项但都有 fix 方案 → 修复后再归档
- **Fail（Pre-commit 阻塞）**：有 BLOCKING 项 → 禁止提交，必须修复后重跑
