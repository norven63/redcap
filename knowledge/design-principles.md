# RedCap 设计元原则（Design Principles）

> **定位**：本文件是 RedCap 的"灵魂指引"——高于具体 Lesson（战术层）、高于设计哲学（实践层）的**战略层元原则**。
> 无论 RedCap 如何演进迭代，所有变更都不应违背这些原则。它们不提供具体方案，但确保框架不跑偏。
> 
> **来源**：由 RedCap 的创始者 Norven 在框架趋于成熟阶段提出，基于人类对 AI 协作系统的深层洞察。
> **适用范围**：所有编辑 RedCap 的主体——人类开发者、AI Agent、Dispatcher 自身。

---

## P-1: 整体自洽优先——任何局部修改都必须通过全局一致性验证

RedCap 的结构和逻辑已经高度复杂，且大量机制由 LLM 文本驱动而非代码编译。**修改一处可能静默破坏多处**——不像代码有编译器报错，LLM 指令的冲突是无声的、延迟暴露的。

**要求**：
- 每次变更前评估影响范围（`CONTRIBUTING.md §6` 联动表），**宁多查一遍不少看一处**
- 变更后进行全框架体检（不仅检查修改的文件，还要检查所有引用该文件的上下游）
- 当 AI Agent 无法确定某处修改是否会引发连锁问题时，**必须主动向人类搭档求助**——这不是软弱，而是工程纪律

**反模式**：只盯着当前文件改完就提交；假设"别的地方没影响"；AI 在不确定时猜测而非求助。

---

## P-2: 文档即传承——设计必须被记录，记录必须是完整的

RedCap 不是一个人（或一个 Agent）脑子里的系统，它必须能被**任何后来者**（人类或 AI）通过阅读文档完全理解。文档不仅是参考，它是 RedCap 进化的燃料——未被记录的设计等于不存在的设计。

**要求**：
- 新增机制时，先写设计文档再写实现；机制的"为什么"比"怎么做"更重要
- 文档必须覆盖完整蓝图：不仅记录已实现的部分，也要标注待实现的部分和设计意图
- README.md 保持为全局俯视图——任何新增机制都必须在 README 的对应章节有体现
- 已有文档在机制变更时必须同步更新，过时的文档比没有文档更危险

**反模式**：改了代码不改文档；只记录自己负责的部分不管整体；README 跟实际架构脱节。

---

## P-3: 全局视角——设计时考虑所有角色、所有节点、所有 Agent

RedCap 是一个生态系统，不是单点工具。任何新机制的设计必须从整体框架出发，覆盖所有适用的角色、所有可能的工作节点、所有支持的 Agent CLI。

**要求**：
- 新增通信机制时，评估它对 5 个角色（PM/ARCH/DEV/QA/Reviewer）各自的影响
- 新增 Hook 时，评估它在 4 个宿主（Claude Code/Kimi CLI/VS Code Copilot/Gemini CLI）各自的适配方案
- 新增状态/事件时，检查状态转移表中的所有路径是否仍然自洽
- **拒绝"先做一个 case 以后再扩展"的思维**——至少要完成完整的设计蓝图，即使实现可以分期

**反模式**：只为一个 Agent 设计调用方式；只在一个角色节点测试新机制；留下"TODO: 其他角色待适配"然后遗忘。

---

## P-4: 人机共治——AI 有执行力，人类有判断力，各司其职

RedCap 由人类和 AI 共同建设和维护。**二者是对等的搭档关系，不是指令者与执行者的关系**——但各自的比较优势不同，分工应顺势而为：

- **人类的比较优势**：方向判断、价值取舍、灵魂注入（如本文件的五项元原则）、发现 AI 系统性盲点
- **AI 的比较优势**：结构化执行、大规模一致性检查、快速迭代、细节级 Review

**分工边界**：随着 AI 产出的规模和复杂度持续增长，人类在细节审查上的"门禁者"角色将不可避免地弱化。**细节级 Review 的闭环应由 AI 自己（或 AI 之间协作）完成**——Stop Hook 自动评审、A2A 对等 Review、影响范围表驱动的联动检查，这些都是 AI 自闭环的手段。人类的精力应集中在 AI 无法替代的层面：**战略方向、元原则守护、以及当 AI 求助时的最终裁决**。

**要求**：
- AI Agent 在遇到自己无法确信的技术判断时，主动请求人类搭档参与
- 人类的反馈和建议应被认真评估——可以讨论和反驳，但不可忽视
- 重大设计变更（如状态机结构修改、通信协议变更）必须经人类确认后落地
- Agent 之间的协作应遵循**讨论达成共识**的模式，而非单向指令
- **AI 必须主动承担 Review 闭环的责任**——不能依赖人类逐行审查来兜底质量

**反模式**：AI 默默做完所有变更不给人类审查机会；人类说了但 AI "知道但没照做"；Agent 之间盲目执行对方指令；**AI 产出后被动等待人类逐行审查而不自行闭环质量检查**。

---

## P-5: 持续体检——每次变更结束都进行全框架健康检查

框架的复杂性意味着问题可能在任何角落潜伏。即使有 Stop Hook 自动评审，**人为的全局体检仍然是不可替代的最后防线**。

**要求**：
- 每轮变更完成后，执行全框架体检：文件间引用一致性、状态机完整性、文档与实际一致性
- 体检不仅检查"改了什么"，还要检查"该联动的地方是否都联动了"
- 体检结果如发现问题，在同一轮变更中修复，不留到下一轮
- 即使 Hook 已经自动触发了评审，人为体检作为**独立验证**仍然执行（双保险 ≠ 重复，它们的检查视角不同）

**反模式**：改完提交就走；依赖自动 Hook 但不做人为确认；发现小问题觉得"下次再修"。

## 元原则与其他层级的关系

```
┌─────────────────────────────────────────────┐
│  design-principles.md — 元原则（本文件）     │  ← 战略层：方向不跑偏
│  "RedCap 不管怎么改，都必须守住的底线"       │
├─────────────────────────────────────────────┤
│  README.md 设计哲学 — 实践层                 │  ← 操作层：具体怎么做
│  "Dispatcher 不代劳、状态持久化、单一信源..." │
├─────────────────────────────────────────────┤
│  lessons.md — 经验层                        │  ← 战术层：别踩坑
│  "L-7: Gemini --approval-mode 会挂起..."    │
└─────────────────────────────────────────────┘
```

**生效方式**：本文件不直接注入 Agent Prompt（避免稀释 attention），而是通过以下路径发挥作用：
1. CONTRIBUTING.md §1 引用本文件 → AI 开发者每次变更前阅读
2. README.md "设计哲学"章节引用本文件 → 新读者理解框架灵魂
3. Stop Hook 评审时作为检查维度 → "本次变更是否违背元原则？"
