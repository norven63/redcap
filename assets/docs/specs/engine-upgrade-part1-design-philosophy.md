> **文档性质**：技术设计哲学与架构决策记录  
> **版本**：v1.0 Draft  
> **日期**：2026-03-28

## 1. 问题陈述

### 1.1 现状

RedCap 当前的执行模型是**单 AI 串演模式**：一个 AI Agent 按照角色手册（产品经理 → 架构师 → 程序员 → 测试QA）依次切换身份，在同一个对话上下文中完成所有角色的工作。

这个模型在以下方面表现良好：
- 角色流转规则清晰、已验证
- 文档体系完善、模板齐全
- 质量门禁（回退矩阵、Git 规范、安全铁律）健全

但它也触碰到了天花板：

| 瓶颈 | 具体表现 |
|------|---------|
| **上下文容量** | 一个 AI 要装下需求文档、设计文件、全部代码、测试用例——项目一复杂就超限 |
| **角色串味** | 程序员阶段的 500 行 diff 会干扰后续测试阶段的判断；设计讨论会被代码细节淹没 |
| **串行瓶颈** | 只有一个 AI 在工作，无法利用多个 Agent 工具的并行能力 |
| **认知负荷** | 同一个上下文要在"产品思维"与"工程思维"之间反复跳跃，角色边界容易模糊 |

### 1.2 目标

将 RedCap 从"单 AI 串演"升级为**多 Agent 协同执行**：

- 每个角色由独立的 Agent 进程承担，拥有独立的上下文空间
- 角色之间通过文件系统中的交付物进行通信，互不干扰
- 整个流程可自动推进，仅在必要时（需要真实凭证、无法决策等）中断让用户介入
- 当前需支持 Claude Code CLI 和 Gemini CLI 两个 Agent 工具

### 1.3 核心约束

升级必须**保持 RedCap 已有的角色定义、流转规则、文档体系、质量门禁不变**。我们改变的是"谁来扮演角色"和"角色之间如何通信"——即执行引擎，而非业务规则。

## 2. 核心设计原则

本次升级的架构决策由五个设计原则驱动。每个原则均源自我们讨论中的具体问题，并有明确的工业界理论支撑。

### 2.1 原则一：进程隔离 — 每个角色拥有独立的上下文空间

**问题**：同一个 Agent 工具（如 Claude Code）可能需要扮演多个角色。如果共享同一个对话 session，架构师的设计讨论和程序员的代码 diff 会互相污染上下文。

**决策**：每个角色 × 每个步骤 = 一个独立的 Agent Session。

**工业界对应**：这就是操作系统的**进程地址空间隔离**。每个进程拥有独立的虚拟内存，不能随意读写其他进程的数据。原因完全一样——防止互相干扰、限制故障传播。

```
操作系统：                              RedCap 引擎：
┌─────────────┐ ┌─────────────┐        ┌──────────────┐ ┌──────────────┐
│ Process A   │ │ Process B   │        │ 架构师 Session│ │ 程序员 Session│
│ 独立内存    │ │ 独立内存    │        │ 独立上下文    │ │ 独立上下文    │
│ 独立权限    │ │ 独立权限    │        │ 只读代码库    │ │ 读写代码库    │
└─────────────┘ └─────────────┘        └──────────────┘ └──────────────┘
  不能访问B的内存  不能访问A的内存       不含代码diff    不含设计讨论
```

**三层隔离价值**：
1. **认知纯净** — 每个 session 的对话历史只包含自己角色相关的内容
2. **权限最小化** — 不同 session 可配置不同的工具权限（架构师不执行代码，程序员不改需求文档）
3. **Token 效率** — 每个 session 的上下文消耗独立计算，不会因混杂其他角色内容而过早耗尽

### 2.2 原则二：去中心化责任链 — 角色只知道上下游，不知道全局

**问题**：如果设置一个"中心化项目经理"来分配所有任务、转发所有产出，这个角色会成为系统瓶颈——它要理解所有角色的所有产出，上下文消耗等于所有角色之和，还会造成信息经"翻译"后的损耗。

**决策**：每个角色只关心两件事——我的上游是谁（从哪里接收输入）、我的下游是谁（把产出交给谁）。不存在一个"全知全能"的中心调度角色。

**工业界对应**：这个设计同时映射了三个经典概念：

**Actor Model（Erlang/Akka）**：

| Actor Model 概念 | RedCap 对应 |
|-----------------|------------|
| Actor（演员） | 每个角色 |
| Mailbox（邮箱） | 角色的交付物收件箱 |
| Message（消息） | 交付物（需求文档、设计文档、代码、测试报告） |
| Behavior（行为） | 角色的操作手册 |
| 无共享状态 | 独立 session + 独立工作目录 |

**Unix Pipeline 哲学**：

```
cat requirements | architect | programmer | qa > delivery
```

每个角色如同管道中的一个命令——从 stdin（上游交付物）读入，向 stdout（下游交付物）写出，做好一件事，不关心管道中其他命令的存在。

**责任链模式（Chain of Responsibility, GoF）**：

双向责任链的变体——正向传递任务，反向传递确认或升级请求。每个节点只知道自己的下一个（和上一个）节点。

### 2.3 原则三：文件系统即通信协议 — 交付物是唯一的进程间通信方式

**问题**：角色之间如何传递信息？Agent CLI 调用之间没有内存共享，也没有网络连接。

**决策**：角色之间的一切通信都通过**文件系统中的交付物**完成。一个角色写文件到指定目录，下一个角色从该目录读取。

**工业界对应**：这是操作系统中 **IPC（进程间通信）** 的文件系统实现方式。在 Unix 世界中，`/tmp`、管道文件、共享目录历来就是最简单也最可靠的进程间数据交换方式。

```
架构师完成设计 → 写入 architect/outbox/ → 文件落盘
                                          ↓  （文件系统 = 消息队列）
程序员接收任务 ← 读取 architect/outbox/ ← 文件存在即可读
```

**为什么不用更"高级"的通信方式**：

| 方案 | 为什么不用 |
|------|-----------|
| 通过 Dispatcher 转发内容 | Dispatcher 要存储全量内容，变成中心化瓶颈 |
| Agent A 直接调用 Agent B 的 CLI | 嵌套调用会导致控制权丧失、上下文叠加、审计黑洞 |
| 数据库 / Redis | 过度工程，文件系统已原生可用且零额外依赖 |

文件系统作为通信层的优势：
1. **零配置** — 不需要安装任何中间件
2. **天然持久化** — 断电重启后交付物仍在
3. **可审计** — 每个角色写了什么、改了什么，ls 一下就能看到
4. **所有 Agent CLI 原生支持** — Claude Code 和 Gemini CLI 都能读写文件

### 2.4 原则四：Dispatcher 是基础设施，不是角色 — 路由器类比

**问题**：如果所有角色都是独立的、去中心化的，那谁来"踢一脚"启动下一个角色？文件写到目录里了，但文件不会自己调用 CLI 命令。

**决策**：由当前与用户对话的 AI 充当 Dispatcher——但它**不是一个业务角色**，而是使整个系统运转的**基础设施层**。

**为什么不能是"项目经理"角色**：
- 如果 Dispatcher 是一个 Agent session，谁来启动它？→ 无穷递归
- 如果它要"理解"任务内容才能调度，它就变成了中心化瓶颈
- 项目经理是"团队中的人"，Dispatcher 是"让团队运转的机制"

**核心类比：路由器**

互联网是公认的去中心化架构，但每一次通信都要经过路由器。路由器的存在不违反去中心化——因为：

| 路由器的特征 | Dispatcher 的对应 |
|------------|------------------|
| 不理解数据包内容（不看网页内容、不听语音通话） | 不理解交付物内容（不看需求文档、不看代码） |
| 只看目标地址（IP header） | 只看状态标记（status 字段） |
| 查路由表做转发决策 | 查状态转移表做路由决策 |
| 不是网络中的一个"节点"，是使网络运转的基础设施 | 不是团队中的一个"角色"，是使流转运转的引擎 |

**试金石**：如果把 Dispatcher 的逻辑改成一段 50 行的 Python 脚本（读状态 → 查表 → 启动下一个 CLI → 读返回 → 更新状态），系统一样能跑。它不需要是 AI。之所以由输入 AI 执行，是因为输入 AI 恰好有终端能力，且在某些时刻需要切换到"产品经理"身份与用户沟通。

**驱动模式：同步事件循环**

Dispatcher 不需要轮询。CLI 调用是同步阻塞的——发命令 → Agent 执行 → 返回结果 → 控制权自动回到 Dispatcher。这和操作系统的**进程调度器**（Scheduler）是同一模式：调度器不运行用户程序的逻辑，它只在上一个进程让出 CPU 后决定"下一个运行哪个进程"。

对应的工业界模式：

| 模式 | 核心理念 |
|------|---------|
| Kubernetes Reconciliation Loop | 读期望状态 → 对比实际状态 → 执行动作 → 重复 |
| Temporal Workflow Engine | 定义步骤 → 引擎依次执行 → 步骤间持久化状态 |
| 有限状态机（FSM） | 当前状态 + 事件 → 转移到新状态 |

### 2.5 原则五：工作空间隔离 — 每个角色拥有独立的文件空间

**问题**：如果所有角色的工作记录、草稿、进展都混在一起，会出现和"上下文污染"类似的问题——信息噪声，以及误读/误改其他角色的文件。

**决策**：在两个层面实施空间隔离——

| 层面 | 隔离内容 | 共享内容 |
|------|---------|---------|
| **RedCap 框架层** | 每个角色的操作手册（handbook）互相独立 | 安全铁律、代码规范等共享规范 |
| **开发项目层** | 每个角色的工作区（草稿、日志）互相独立 | 源码、交付物（通过 outbox 机制） |

**工业界对应**：这与操作系统的进程隔离 + IPC 模型完全一致——

| OS 概念 | RedCap 对应 |
|---------|------------|
| 进程地址空间（私有内存） | 角色的独立工作目录 |
| 内存保护（不能随意访问其他进程） | 角色只写自己的 workspace，只读上游的 outbox |
| IPC 机制（管道、共享内存） | outbox/ = 消息队列；shared/ = 只读共享区 |
| 进程状态（Running/Ready/Blocked） | state.yaml 中的角色状态 |

同时也呼应了**康威定律（Conway's Law）** 的反向运用：先定义好通信结构（职责链 + 隔离空间 + 交付物协议），系统自然会按这个结构运转。

## 3. 物理调用拓扑 vs 逻辑交付拓扑

经过前述五个原则的推导，我们需要明确一个关键区分：**角色看到的逻辑世界**和**系统实际的物理执行**是两个不同的视角。

### 3.1 逻辑视角（角色所见）

```
产品经理 ──交付物──→ 架构师 ──交付物──→ 程序员 ──交付物──→ 测试QA
                                                           │
   ↑                   ↑                ↑                  │
   └───────────────────┴────────────────┴──────────────────┘
              回退/确认/升级：只找上游
```

每个角色：
- 不知道 Dispatcher 的存在（对角色透明）
- 不知道自己是怎么被启动的
- 只知道"我的输入从哪个目录读，我的输出写到哪个目录"
- 只知道"如果有问题，按根因类型找对应上游"

### 3.2 物理视角（实际执行）

```
                 ┌─────────────────────┐
                 │  输入 AI（Dispatcher）│
                 └──┬──┬──┬──┬────────┘
                ①/ ③/ ⑤/ ⑦/
                /② /④ /⑥ /⑧
               ↓↑  ↓↑  ↓↑  ↓↑
               PM  Arch Dev  QA

① 启动产品经理 CLI → ② 接收返回
③ 启动架构师 CLI   → ④ 接收返回
⑤ 启动程序员 CLI   → ⑥ 接收返回
⑦ 启动测试QA CLI  → ⑧ 接收返回
```

所有 Agent CLI 都由 Dispatcher 逐一启动。Agent 之间不直接相互调用。这是**星型的物理拓扑 + 链式的逻辑拓扑**——正如互联网中，逻辑上是端到端通信，物理上每一跳都经过路由器。

## 4. 升级前后对比

| 维度 | 当前版本（单 AI 串演） | 升级后（多 Agent 协同） |
|------|---------------------|----------------------|
| **执行者** | 1 个 AI 切换 Prompt 扮演 4 角色 | 独立 Agent 进程各自承担 1 角色 |
| **上下文策略** | 全部挤在一个对话中 | 每角色 × 每步骤 = 独立 Session |
| **角色切换** | Prompt 指令切换 | CLI 进程切换（物理隔离） |
| **通信方式** | 同一上下文内直接引用 | 文件系统交付物（IPC） |
| **用户介入频度** | 每个角色阶段需确认"通过" | 仅在需要提供信息或无法决策时 |
| **状态管理** | 对话上下文 + 文档 | state.yaml + Session 持久化 + 文档 |
| **可观测性** | 对话记录 | state.yaml + 各角色 outbox + Agent 独立 Session 日志 |

### 保持不变的部分

以下 RedCap 核心资产**在本次升级中不改变其业务语义**，仅在执行层面适配新的多 Agent 架构：

- 四角色定义及其职责边界
- 正向流转与反馈回退的状态转移规则
- 根因 → 责任角色的回退矩阵
- 文档体系（`/开发手册/` 下的固定文件与 `designs/` 目录）
- 安全铁律、代码规范
- Git 门禁与格式规范
- 测试分工（程序员自测 vs QA 验收的边界）

## 5. 升级决策机制

多 Agent 自动执行意味着需要一套明确的决策分级，确保系统在遇到不确定性时能正确升级而非盲目推进。

### 5.1 三级决策模型

```
Level 0: Agent 自决策（不升级）
  · 技术实现细节的选择（变量命名、等价方案二选一等）
  · 不影响上下游的局部决定

Level 1: 升级到产品经理角色
  · 需求边界不清晰
  · 技术方案影响产品体验
  · 跨角色矛盾（架构师设计 vs 程序员认为不可行）
  · 产品经理做出决策后，结论回传给发起升级的角色

Level 2: 升级到用户（暂停流程）
  · 需要真实凭证、密钥、ID 等用户掌握的信息
  · 产品经理也无法判断的商业决策
  · 潜在的不可逆操作（删除数据、部署到生产环境）
  · 成本 / 预算相关决策
```

### 5.2 升级信号的传递方式

Agent 通过返回结果中的结构化字段发出升级信号：

```
status: "blocked"
escalation:
  level: 1 或 2
  question: "具体问题描述"
  impact: "对流程的影响"
  recommendation: "Agent 自己的建议（如有）"
```

Dispatcher 收到后：
- Level 1 → 启动产品经理 Session 进行决策
- Level 2 → 暂停流程，将问题转述给用户

## 6. 技术可行性基础

本方案的可行性依赖于以下已验证的技术事实：

### 6.1 CLI 非交互模式

两个 Agent 工具均支持非交互（headless）模式，可从终端命令调用并获取结构化输出：

| 能力 | Claude Code | Gemini CLI |
|------|-------------|------------|
| 非交互模式 | `-p` / `--print` | `-p` / `--prompt` |
| JSON 输出 | `--output-format json` | `--output-format json` |
| System Prompt | `--system-prompt` | `--policy` |
| 目录访问 | `--add-dir` | `--include-directories` |
| 权限控制 | `--permission-mode`, `--allowedTools` | `--approval-mode` |

> **底层模型说明**：当前环境中 Claude Code CLI 通过 SiliconFlow 代理接入 **Kimi 2.5**（Moonshot AI）模型，而非 Claude 原生模型。CLI 的工具链能力（文件读写、Bash 执行、权限控制等）不受影响，但 AI 推理与生成能力以 Kimi 2.5 为准。Gemini CLI 使用 Gemini 3 Pro 原生模型。Agent 路由策略基于两个底层模型的实际能力进行规划（详见第二篇 §5.1）。

### 6.2 Session 持久化

两个工具均原生支持非交互模式下的会话持久化：

| 能力 | Claude Code | Gemini CLI |
|------|-------------|------------|
| 自动保存会话 | 默认开启（`--no-session-persistence` 可关闭） | 默认开启 |
| 指定 Session ID | `--session-id <uuid>` | 自动分配 |
| 恢复会话 | `--resume <session-id>` | `--resume <index\|latest>` |
| 会话列表 | `~/.claude/projects/` 目录 | `--list-sessions` |

### 6.3 同步阻塞调用

CLI 调用是同步的——命令发出后阻塞等待，Agent 内部完成所有工作后输出结果到 stdout，进程退出，控制权回到调用方。调用方可以完整接收返回的 JSON 数据。这一点已在实际环境中验证通过。

## 7. 关键风险与应对

| # | 风险 | 严重度 | 应对策略 |
|---|------|--------|---------|
| 1 | Agent 误操作（删除不该删的文件） | 高 | 通过 `--permission-mode` 和 `--allowedTools` 限制工具权限；Git 作为安全网 |
| 2 | Agent 输出格式不一致 | 中 | Claude Code 可用 `--json-schema` 强制校验；Gemini 通过 prompt 约束 + Dispatcher 做 fallback 解析 |
| 3 | 上下文窗口溢出 | 中 | 每角色 × 每步骤独立 Session；必要时放弃旧 Session 开新的并注入摘要 |
| 4 | 错误沿流水线累积 | 中 | 每个角色切换点做自动化 Quality Gate（lint、test、diff review） |
| 5 | Agent CLI 进程超时 | 低 | 设置合理 timeout；角色手册中规定单次任务的复杂度边界 |
