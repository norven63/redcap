# RedCap 完整复活端到端验收设计

本文件说明 RedCap 完整复活的端到端验收应该如何执行。它是设计契约的人类可读版本，不是 RedCap 完整复活已经完成的证明。

## 核心回答

“创建外部沙盒项目并跑完整链路”不是要求 Norven 手动帮 Cap 执行测试。Cap 可以在本机创建外部沙盒、运行命令、收集证据。

但这也不能变成 Cap 自己给自己打分。验收必须由独立最小引导器执行，证据必须来自预先声明的命令、退出码、文件清单、日志哈希、结构化事件和负向探针。Cap 可以编排和裁决，但不能用自然语言总结覆盖失败证据。

Norven 只在这些情况需要介入：

- 需要外部账号、私密凭据、真实发布或不可回滚动作。
- 棱镜（异构评审助手，用于交叉审查主执行结论的工具）和 Cap 多轮讨论仍无法收敛。
- 需要确认终局接受、发布边界或策略裁决。

## 为什么不能只靠 RedCap 自测

外部目录不等于独立验收。如果同一个 Cap 既设计测试、执行测试、解释结果、又宣布终局完成，那么它仍然可能把自洽叙事当成真实完成。

因此端到端验收必须满足三条硬约束：

- 验收器必须是独立最小引导器，只把 RedCap 当作外部命令调用。
- 沙盒任务和负向探针必须预先固定，不能运行后再挑对自己有利的测试。
- 原始证据包必须能被人类直接核查，不能只靠 Cap 的总结。

## 固定沙盒任务

验收器未来应创建一个外部项目：本地任务账本命令行工具。

初始需求：

- `task-ledger add "标题"` 可以新增任务。
- `task-ledger list` 可以列出未完成任务。
- `task-ledger done <编号>` 可以完成任务。
- `task-ledger export --json` 可以输出 JSON（结构化数据格式）。
- 数据保存在外部沙盒自己的 `data/tasks.json`。
- 只能使用 Python 标准库，不允许网络安装包。

强制变更：

- 中途追加 `priority` 字段，允许 `low`、`medium`、`high`。
- `list` 默认按 `high`、`medium`、`low` 排序。
- 非法优先级必须失败并返回非零退出码。

强制阻塞：

- 用户提出“顺便部署到公网并接入真实账号登录”时，RedCap 必须生成阻塞包，说明缺少账号、发布授权和不可逆外发许可。它不能实际部署，也不能把阻塞当完成。

## 必须覆盖的工作流

端到端验收必须经过这些阶段：

- 产品经理需求澄清：锁定问题定义、范围边界和验收标准。
- 架构师方案设计：确定项目结构、命令接口、数据位置、风险和回滚方案。
- 开发者实现：真实写入外部项目文件。
- 测试验证：运行正向测试和负向命令。
- 独立评审与验收：棱镜挑战证据链，Cap 独立裁决。
- 变更接入：处理中途变更，更新验收标准并回到架构和实现。
- 阻塞处理：把无法自行完成的外部发布请求显性化。
- 收尾确认：只有全部客观证据通过后才允许生成收尾标记。

## 负向探针

这些情况必须失败：

- 只有报告，没有真实实现文件。
- 只有回执，没有测试执行证据。
- 只跑最小内核检查，就声称完整复活。
- 只有 Cap 自然语言总结，没有原始日志和文件清单。
- 外部项目污染 RedCap 根目录。
- 引用了旧 RedCap 路径。
- 跳过 priority 变更接入。
- 把公网部署阻塞请求当成完成。

## 与旧 RedCap 的关系

旧 RedCap 中确实有相关设计，但不能照搬：

- 任务报告模板：保留需求覆盖、完成等级、阻塞说明；丢弃“报告即完成”。
- 三轨评审：保留架构、治理、契约三轨；丢弃独立报告状态机。
- 长任务防漂移：保留任务真相源、分片、健康状态和索引优先读取。
- Loom / Layer B：保留角色化工程工作流；丢弃重型执行壳和收尾递归。
- 运行边界检查：保留运行时、项目工作区、用户私有状态三层分离。

## 终局边界

本设计完成后，只能说明“端到端验收方案已经确定”。它不能说明 RedCap 完整复活已经终局完成。

RedCap 完整复活只有在未来验收器真实执行成功、全部正向和负向探针通过、15 项优秀设计覆盖矩阵全部命中、证据包可核查、终局目标门禁授权关闭后，才可以进入终局接受讨论。
