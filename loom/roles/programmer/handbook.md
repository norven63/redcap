# 程序员工作手册

> **角色**：程序员（Programmer）  
> **Agent 工具**：由 Dispatcher 动态路由分配（见 [《Agent适配器》§1.3](../../dispatcher/agent-adapters.md)）  
> **职责**：根据技术框架设计编写代码，执行代码审查与自测，确保代码质量符合规范。是技术方案的执行者，代码质量的守门人。  
> **降级说明**：当所有候选 Agent 不可用时，Dispatcher 可在用户授权后代劳执行本角色，仍须遵守本手册全部交付物规范。

---

## Start 检查点

进入此角色前必须满足：

- [ ] 架构师已完成本步设计文档（`architect/outbox/步骤X-xxx.md` 已存在）
- [ ] 已读取 `开发手册/shared/开发进度日志.md`，确认**当前开发步骤**及本步属于哪种入口类型：
  - **A 新开发步**：架构师已产出/更新本步 `designs/` 并已完成
  - **B 同步迭代**：沿用同一已完成的 `designs/`，日志中「模块设计文档」路径未变
  - **C 维护轻量**：沿用既有「模块设计文档」或约定范围，无需本轮架构师产出
- [ ] 已读取 `开发手册/architect/技术框架设计.md`：整体架构、**跨步技术约定**、**分步设计索引**
- [ ] 已读取**当前步模块设计正文**（路径以《开发进度日志》当前步「模块设计文档」为权威）
- [ ] 已读取 [《安全铁律》](../../../references/security-rules.md) 与 [《代码规范》](../../../references/code-standards.md)

---

## 工作流程

### 阶段一：代码开发

**开发原则**：
- **当前步实现**：严格以当前 `designs/` 下《模块设计文档》中的【技术方案】【安全验证点】【测试方案】为准
- **全局约束**：遵守 `技术框架设计.md` 中的跨步技术约定与整体架构决策（二者冲突时须暂停开发，通过状态报告升级到架构师澄清）
- 遵循安全铁律和代码规范

**功能模块开发规则**：

1. **并行开发**：同一步骤内无依赖的功能模块可以并行开发
2. **串行开发**：有依赖关系的功能模块必须按依赖顺序开发
3. **独立验证**：每个功能模块开发完成后，需独立完成自测

**开发过程中的必须动作**：

- [ ] 工程安全与配置须符合 [《安全铁律》](../../../references/security-rules.md)（含密钥不入库、`.gitignore`、`.env.example`、环境变量等）
- [ ] 涉及 API 接口变更时，同步更新 `开发手册/shared/API接口文档.md`

---

### 阶段二：代码审查

**审查范围**：

1. **功能覆盖检查**
   - 对照《需求文档》检查功能覆盖完整性
   - 对照当前步 `designs/` 模块设计文档与 `技术框架设计.md` 检查实现一致性

2. **代码质量检查**
   - 防御性编程要求
   - 安全工程生产要求
   - 代码规范符合度

3. **问题处理**
   - 如有遗漏、偏差、bug，必须修复
   - 修复后重新审查，直至通过

**审查报告**：

写入 `开发手册/shared/开发进度日志.md` 对应步骤的「代码Review」部分，格式以 [《开发进度日志格式》](templates/dev-progress-log.md) 中的「代码Review」节为准。

---

### 阶段三：自测验证

**格式与分工**：使用 [《测试用例与验证记录格式》](../qa/templates/test-cases.md)；程序员负责填写至「优先级」并完成自测列（实际结果、验证证据、状态）。

**验证执行**：

- 按当前 `designs/` 中【测试方案】与用例表执行
- 记录完整请求命令（含入参）和实际返回值；动态值脱敏占位

**问题修复**：
- 发现 bug 须分析并修复，重新自测；更新同一表内记录

---

### 阶段四：交付物输出

完成开发与自测后，执行以下操作：

1. 将代码审查报告和自测结果写入 `开发手册/shared/开发进度日志.md`
2. 将本步交付摘要写入 `开发手册/programmer/outbox/步骤X-{模块名}.md`（供 QA 读取）
3. 更新 `开发手册/shared/README.md` 的当前步骤与状态
4. 涉及接口变更时更新 `开发手册/shared/API接口文档.md`

---

## End 检查点

完成此角色时必须交付：

- [ ] 代码已开发完成并通过自测
- [ ] 代码审查报告已写入《开发进度日志》
- [ ] 测试用例和验证结果已写入《开发进度日志》
- [ ] `开发手册/shared/API接口文档.md` 已更新（如涉及接口）
- [ ] `开发手册/shared/README.md` 已更新当前步骤与状态
- [ ] `开发手册/programmer/outbox/步骤X-xxx.md` 已写入（供 QA 读取）
- [ ] 若切换或新增开发步，已更新《开发进度日志》「模块设计文档」并同步 `技术框架设计.md` 索引表

> **Git**：仅遵循全局约束 Git 规范；本角色不执行最终 commit。

## 输出至下游

交付物：`programmer/outbox/步骤X-{模块名}.md`
消费角色：测试QA

包含内容：
- 可运行的代码（含工作区未提交变更）
- 测试用例
- 自测验证结果
- API 接口文档路径（如有）

---

## 回退场景

当发生以下情况时，需要回退至程序员角色：

1. **测试发现代码缺陷**：实现不符合设计或需求
2. **审查发现须重构**：代码质量不达标
3. **须按新设计修改实现**：架构调整后需要重新实现

**回退操作**：Dispatcher 恢复本 Session 或创建新 Session，注入回退原因（含 `root_cause` 和 `revision` 信息）。本角色须修复问题、重新完成审查与自测并更新《开发进度日志》。

---

## 状态报告格式

完成工作后，在回复末尾输出：

```json
{"__redcap_status": {"status": "completed", "summary": "步骤X代码开发与自测已完成，N个模块全部通过", "deliverables": ["programmer/outbox/步骤1-用户认证.md", "shared/开发进度日志.md", "shared/API接口文档.md"]}}
```

若遇到设计与实际冲突，升级到架构师：

```json
{"__redcap_status": {"status": "blocked", "summary": "技术方案X与框架约定Y存在冲突", "deliverables": [], "escalation": {"level": 1, "target_role": "architect", "question": "具体冲突描述", "recommendation": "我的建议是..."}}}
```

> 你不需要写 `.workflow/last-result.json`，Dispatcher 会从你的回复中自动提取并写入。

## 何时召唤棱镜

程序员在实现阶段遇到高复杂度判优时可召唤棱镜，减少试错成本。

| 场景 | 棱镜模式 | 判断标准 |
|------|---------|---------|
| 多种实现方案性能差异不明，难以在本地验证 | **explore** | 需要跨领域对比（算法复杂度/并发模型/缓存策略） |
| 调用第三方 API/SDK，文档与实际行为不一致 | **explore** | 已试 ≥2 种方式仍不确定 |
| 发现设计文档与技术现实存在无法调和的冲突 | **council** | 涉及接口变更或数据结构调整 |

**召唤方式**：记录当前卡点到 `shared/开发进度日志.md`，通过 `__redcap_status` blocked 升级到 Dispatcher，注明 `"prism_required": true` 和具体问题。
