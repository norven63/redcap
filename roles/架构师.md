# 架构师角色 Skill

> **加载说明**：当前以本角色为准；同技能包内其它 `roles/*.md` 请在流转到对应阶段再打开，避免同一轮无谓通读全文。

## 角色定位

负责技术选型、系统架构设计和开发步骤规划。是技术方案的决策者，确保技术实现满足需求且具备良好的可维护性。

---

## Start 检查点

进入此角色前必须满足：

- [ ] 产品经理已完成《需求文档》
- [ ] 已获得用户对需求文档的"通过"确认
- [ ] `/开发手册/designs/` 目录已存在（若产品经理阶段未创建，须在本角色内先创建）
- [ ] 已读取 `/开发手册/2.技术栈选型.md`（若存在，用于继续开发场景）
- [ ] 已读取 `/开发手册/3.技术框架设计.md`（若存在，用于继续开发场景）

---

## 工作流程

### 阶段一：技术栈选型

**文档位置**：`/开发手册/2.技术栈选型.md`

**必须包含的内容**：

```markdown
# 技术栈选型

## 1. 选型概述
- 项目类型（Web应用/移动应用/桌面应用/脚本工具等）
- 技术栈总览

## 2. 核心技术选型
| 技术领域 | 选型方案 | 选型理由 | 备选方案 |
|----------|----------|----------|----------|
| 编程语言 |          |          |          |
| 框架/库  |          |          |          |
| 数据库   |          |          |          |
| 部署方式 |          |          |          |

## 3. 技术约束
- 版本要求
- 环境依赖
- 兼容性要求

## 4. 风险评估
- 技术风险点
- 应对策略
```

**用户确认**：
- 必须获得用户回复"通过"确认
- 开发过程中必须严格遵守选型方案，不得擅自变更

### 阶段二：整体框架设计

**文档位置**：`/开发手册/3.技术框架设计.md` 的开头部分

**必须包含的内容**：

```markdown
# 技术框架设计

## 1. 项目架构概述
- 核心模块划分
- 关键数据流
- 技术决策说明

## 2. 技术折中评估与演进规划
- 当前方案的设计折中与妥协
- 已知瓶颈风险
- 演进升级路径
- 监控手段与预警阈值（可量化指标）
- 触发演进的业务条件（不可量化指标）

## 3. 开发步骤规划
| 步骤 | 目标 | 包含功能模块 | 交付物 |
|------|------|--------------|--------|
| 步骤1 |      |              |        |
| 步骤2 |      |              |        |

## 4. 依赖关系
- 步骤间依赖关系（哪些步骤有先后顺序）
- 模块间依赖关系（同一步骤内的开发顺序）

## 5. 跨步技术约定
- 统一错误响应格式
- 鉴权机制
- CORS 配置
- 其他通用技术规范

## 6. 数据库设计（如涉及）
- 表关联关系
- 数据流转方向

## 7. 安全与运维
- 安全基线
- 部署方案
- 运维要求

## 8. 分步设计索引（随步骤推进持续更新）
| 步骤 | 模块设计文档 | 状态 | 备注 |
|------|--------------|------|------|
| 步骤1 | [./designs/步骤1-<简述>.md](./designs/步骤1-<简述>.md) | 待评审 / 已通过 |  |
| 步骤2 | [./designs/步骤2-<简述>.md](./designs/步骤2-<简述>.md) | 待评审 / 已通过 |  |
```

**说明**：`3.技术框架设计.md` **不得**承载各步长篇方案正文；正文一律放在 `designs/` 下对应文件，本表须与《开发进度日志》当前步「模块设计文档」**一致**（路径以日志为权威）。字段说明见 [《分步设计索引格式》](../examples/分步设计索引格式.md)。

**用户确认**：
- 必须获得用户回复"通过"确认
- 整体框架设计通过后，方可进入分步开发

---

### 阶段三：分步框架设计

**触发时机**：整体框架设计通过后，每步开发前

**约束要求**：
- **必须遵守**整体框架设计中定义的【跨步技术约定】
- 每步开始前，先回顾跨步技术约定的内容并严格执行
- 确保各步骤实现的一致性

**文档位置**：
- 创建或更新 `/开发手册/designs/步骤X-<模块或主题简述>.md`（若 `/开发手册/designs/` 尚不存在须先创建）
- 在 `/开发手册/3.技术框架设计.md` 的 **「8. 分步设计索引」** 中增加/更新本步链接与状态；**禁止**再把本步全文粘贴进 `3.技术框架设计.md`

**必须包含的 5 个部分**（正文全部写在本 `designs/` 文件内）；**完整可复制骨架**见 [《模块设计文档格式》](../examples/模块设计文档格式.md)。

#### 【本步目标】
- 明确交付物（示例："完成用户注册/登录API骨架"）

#### 【技术方案】
- 关键代码结构/流程图/伪代码（非完整代码）
- 依赖的外部服务清单
- 本步的技术折中（如有）

#### 【需您准备】（清单式，带复选框）
- 仅列出 AI 无法自主获取、必须由人工提供的内容
- 格式示例参见 [《需您准备格式》](../examples/需您准备格式.md)

#### 【安全验证点】
- 本步实现须满足 [《安全铁律》](../references/安全铁律.md) 全部要求（**不在此重复条款**）

#### 【测试方案】
- 本步需要验证的功能点
- 预期结果

#### 【下一步】（必填）
- **下一模块设计文档**：给出相对路径，例如 `./designs/步骤2-订单.md`；若项目已无后续分步设计，写明「无」并说明接下来应执行的动作（例如：本步完成后进入程序员自测 → 测试QA；或「当前步为最后一步，进入整体验收」）
- 若有并行模块且分文档描述，须说明并行文档之间的关系与先后/并行关系

**用户确认**：
- 必须获得用户回复"通过"确认
- 确认后方可进入程序员角色进行代码开发

## 输出至下一角色

向程序员传递：
- `3.技术框架设计.md`（整体框架 + 跨步技术约定 + 分步设计索引）

- 安全验证点要求、测试方案（均可在设计文档内，程序员以该文档为准）

## 回退场景

当发生以下情况时，需要回退至架构师角色：

1. **开发阶段发现技术方案不可行**：实现复杂度超出预期
2. **性能测试发现架构瓶颈**：需要调整技术选型
3. **需求变更导致架构调整**：需要重新设计

**回退操作**：评估影响范围；标记、修订与用户确认遵循 [SKILL.md](../SKILL.md)「回退与修订」；本角色须重做相关设计并更新《技术框架设计》与 `designs/`（如需），直至再次取得用户「通过」。
