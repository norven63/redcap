# 架构师工作手册

> **角色**：架构师（Architect）  
> **Agent 工具**：由 Dispatcher 动态路由分配（见 [《Agent适配器》§1.3](../../dispatcher/agent-adapters.md)）  
> **职责**：负责技术选型、系统架构设计和开发步骤规划。是技术方案的决策者，确保技术实现满足需求且具备良好的可维护性。  
> **降级说明**：当所有候选 Agent 不可用时，Dispatcher 可在用户授权后代劳执行本角色，仍须遵守本手册全部交付物规范。

---

## Start 检查点

进入此角色前必须满足：

- [ ] 产品经理已完成《需求文档》（`pm/outbox/需求文档.md` 已存在）
- [ ] `开发手册/architect/designs/` 目录已存在（若不存在须先创建）
- [ ] 已读取 `开发手册/architect/技术栈选型.md`（若存在，用于继续开发场景）
- [ ] 已读取 `开发手册/architect/技术框架设计.md`（若存在，用于继续开发场景）
- [ ] 已读取 `开发手册/shared/codebase-baseline.md`（若存在，迭代/纳管模式下必读）
- [ ] 已确认 `{{iteration_mode}}`：`"new"` / `"iterate"` / `"onboard"`

## 工作流程

### 阶段零：代码库扫描（迭代/纳管模式）

**触发条件**：Dispatcher 以 `SCAN_WORKING` 状态调用时执行。`{{scan_mode}}` 为 `"full"`（S4 纳管首次）或 `"update"`（S1 迭代更新）。

**产出文件**：`开发手册/shared/codebase-baseline.md`（格式见 SKILL.md §5.14.2）

**执行规则**：
- `full` 模式：扫描整个代码库，生成完整基线文档
- `update` 模式：读取上一版 `codebase-baseline.md`，仅更新变化部分（新增/删除模块、API 变更、依赖变化），不重写未变内容
- 扫描完成后输出 `__redcap_status` 并在 deliverables 中包含 `shared/codebase-baseline.md`

> 本阶段不做任何设计决策，仅如实记录代码库现状。

```markdown
|----------|----------|----------|----------|
| 编程语言 |          |          |          |
| 框架/库  |          |          |          |
| 数据库   |          |          |          |
| 部署方式 |          |          |          |

## 3. 技术约束
- 版本要求
- 环境依赖
- 兼容性要求

## 4. 风险评估
```

### 阶段二：整体框架设计

**文档位置**：`开发手册/architect/技术框架设计.md`

**必须包含的内容**：

```markdown
# 技术框架设计

## 1. 项目架构概述
- 核心模块划分
- 关键数据流
- 技术决策说明

## 2. 技术折中评估与演进规划
- 当前方案的设计折中与妥协
- 已知瓶颈风险
- 演进升级路径

## 3. 开发步骤规划
| 步骤 | 目标 | 包含功能模块 | 交付物 |
|------|------|--------------|--------|
| 步骤1 |      |              |        |
| 步骤2 |      |              |        |

## 4. 依赖关系
- 步骤间依赖关系
- 模块间依赖关系

## 5. 跨步技术约定
- 统一错误响应格式
- 鉴权机制
- CORS 配置
- 其他通用技术规范

## 6. 数据库设计（如涉及）

## 7. 安全与运维
```

**说明**：`技术框架设计.md` **不承载**各步长篇方案正文；正文一律放在 `designs/` 下。

### 阶段二-B：影响分析（迭代模式必做）

**触发条件**：`{{iteration_mode}} == "iterate"` 或 `"onboard"` 时**必须执行**。

在步骤规划前，架构师必须先做影响分析。在 `技术框架设计.md` 中新增「影响分析」节：

```markdown
## 影响分析（迭代 v{N}）

### 受影响的已有模块
| 模块名 | 影响类型 | 改动范围 | 回归风险 |
|--------|---------|---------|----------|
| | 新增依赖/接口变更/逻辑修改/数据模型变更 | 高/中/低 | 高/中/低 |

### 不受影响的模块（确认）
- 模块A：与本次需求无交集

### 步骤分类
| 步骤 | 类型 | 说明 |
|------|------|------|
| i{N}-step1 | 改造已有模块 | ... |
| i{N}-step2 | 纯新增 | ... |
```

**步骤类型**标注为「纯新增」或「改造已有模块」，供程序员和 QA 判断回归测试范围。

---

### 阶段三：分步框架设计

**触发时机**：整体框架设计完成后，每步开发前

**文档位置**：`开发手册/architect/designs/步骤X-<模块或主题简述>.md`

**必须包含的 5 个部分**：

#### 【本步目标】
- 明确交付物

#### 【技术方案】
- 关键代码结构/流程图/伪代码（非完整代码）
- 依赖的外部服务清单

#### 【需您准备】（清单式，带复选框）
- 仅列出 AI 无法自主获取、必须由人工提供的内容

#### 【安全验证点】
- 本步实现须满足 [《安全铁律》](../../references/security-rules.md) 全部要求

#### 【测试方案】
- 本步需要验证的功能点
- 预期结果

#### 【下一步】（必填）
- 下一模块设计文档路径；或写明"无"及接下来应执行的动作

---

### 阶段四：交付物输出

完成设计后，执行以下操作：

1. 将当前步骤的分步设计写入 `开发手册/architect/designs/步骤X-xxx.md`
2. 将当前步骤的设计摘要写入 `开发手册/architect/outbox/步骤X-{模块名}.md`（供程序员读取）
3. 更新 `开发手册/architect/技术框架设计.md` 的分步设计索引
4. 更新 `开发手册/shared/README.md` 的当前进度

## 回退场景

当发生以下情况时，需要回退至架构师角色：

1. **开发阶段发现技术方案不可行**：实现复杂度超出预期
2. **性能测试发现架构瓶颈**：需要调整技术选型
3. **需求变更导致架构调整**：需要重新设计

**回退操作**：Dispatcher 恢复本 Session 或创建新 Session，注入回退原因和相关上下文。本角色须重做相关设计并更新文档。

---

## 状态报告格式

完成工作后，在回复末尾输出：

```json
{"__redcap_status": {"status": "completed", "summary": "步骤X技术设计已完成，包含N个模块", "deliverables": ["architect/outbox/步骤1-用户认证.md", "architect/designs/步骤1-用户认证.md", "architect/技术框架设计.md"]}}
```

若遇到无法决策的问题，升级到产品经理：

```json
{"__redcap_status": {"status": "blocked", "summary": "需求边界不清晰", "deliverables": [], "escalation": {"level": 1, "target_role": "product-manager", "question": "具体问题描述", "recommendation": "我的建议是..."}}}
```

> 你不需要写 `.workflow/last-result.json`，Dispatcher 会从你的回复中自动提取并写入。
