### L-163: 经验沉淀的失效点常在发现与候选化
- **问题源**：`human-product-surface` 递归 diagnose 的进程风暴已经修复并写入 lesson，但最初不是 RedCap 自动触发沉淀，而是用户人工提醒后才补上。根因不是候选池 schema 或 strict check 完全坏掉，而是第一步“发现这件事必须进入候选判断”仍靠当前 Agent 想起来；`redcap-evolution-harvest-check` 又只对 `governance_tranche: true` 强制检查，导致 `review_tranche`、bugfix、发布安全和用户纠偏类任务可以静默跳过。
- **解决方案**：把 Evolution harvest 前移成“高价值信号门”：review / governance / architecture 标记、发布安全、测试失败、用户纠偏、Prism verdict、closeout blocker、递归/进程风暴、隐私/安全等信号一旦出现，任务报告必须给出 `7.3 Evolution Factory 候选处理`，并明确 `promoted`、`no-promote-with-reason` 或 `deferred-with-owner`。候选池 strict check 只负责“已登记候选是否收口”，不能再冒充“该登记的都已经发现”。
- **最后效果**：RedCap 的经验沉淀从“登记后能管住”向“该登记时先被拦住”推进了一层。后续同类高价值 bug 即使作者没有主动想起 lessons，也会在 diagnose / closeout / spec-check 路径上被要求给出候选处理结论。
- **来源**：2026-05-17 用户追问“重要 bug 为什么没有自动沉淀”与 `human-product-surface` 递归诊断复盘
- **影响度**：high
- **复现次数**：多次
