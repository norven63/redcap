# Hook 失效链路排查与加固设计

**日期**：2026-04-11  
**主题**：由“结果报告未按模板 / 飞书通知缺失”反推 Hook 机制与相邻防线的系统性排查

**当前阶段**：设计 / 排查方案定义（不进入实现）

## 1. 问题陈述

本轮暴露出的两个表面症状是：

1. 任务完成后的结果报告没有按 `references/task-report-template.md` 回报。
2. 规则要求的飞书完成通知没有出现。

这两个问题本身不一定严重，但它们共同指向一个更危险的信号：**RedCap 当前“完成收尾”并不是由单一确定性机制保障，而是混合了流程内强制步骤、宿主 Hook、脚本兜底、文档承诺和人工记忆。只要其中一环漂移，就会出现“看似完成、实则缺步骤”的静默失败。**

本设计的目标不是直接修某一个脚本，而是先回答三个问题：

1. **主链是谁负责**：结果报告、飞书通知、独立评审、清理动作，分别由谁触发？
2. **兜底是否真实存在**：主链失效时，Hook / 审计 / 下次启动检查是否真能补救？
3. **文档与现实是否漂移**：文档中宣称存在的 Hook、模板、宿主覆盖率，在当前仓库里是否真的注册、部署、可触发？

---

## 2. 已知初始信号

在正式实现前（以下条目均为**修复前快照**），代码库里已经能看到几处高风险漂移：

1. `references/task-report-template.md` 明确定义了 RedCap 自身开发任务的标准完成报告，但当前没有发现任何脚本或 Hook 对“是否按模板输出”做机器检查。
2. `compass/CONTRIBUTING.md §5` 明确写的是：**Layer B（开发 RedCap 自身）的飞书通知不是 Dispatcher 自动 hook，而是流程内必须自动执行**。这意味着飞书缺失未必是 Hook 脚本坏了，也可能是主链根本没被调用。
3. 修复前快照中，Claude Stop 链仍同时涉及 `redcap-on-stop-review.sh` 与历史兼容脚本 `redcap-claude-hook-stop.sh`；而 `.gemini/settings.json` 挂的是 `loom/tools/redcap-layerA-session-end.sh`，它会分发到 Layer B 评审，却不天然等价于 Layer B 的成功通知兜底。
4. 修复前文档曾声称 Copilot CLI 可用仓库级 `.github/hooks/`，但当时仓库里尚不存在 `.github/hooks/` 目录，说明“文档承诺 vs 实际注册”至少有一处明显断裂。

这些信号足以说明：**本次排查必须查链路，不是查单点。**

## 3. 方案选项

### 方案 A — 只做 Layer B 快速止血

只排查 RedCap 自身开发链路：完成报告模板、飞书通知、Claude/Gemini 的 Layer B hook、完成后提示。

**优点**
- 收敛快，能尽快堵住当前已暴露的问题。
- 对用户当前观感改善最快。

**缺点**
- 很容易漏掉“相邻机制也在漂移”的问题。
- 无法回答 Copilot / Layer A / Prism 收尾链路是否也在同类失效。

### 方案 B — 直接做全量 Hook 普查

一次性覆盖 Layer A / Layer B / Prism / Claude / Gemini / Copilot / 文档 / 配置 / 脚本 / 运行时契约。

**优点**
- 全面，最适合做系统性清算。
- 能一次产出完整风险版图。

**缺点**
- 进入门槛高，当前已暴露的两个问题会和大量相邻问题混在一起。
- 若不先止血，用户当前最关心的缺陷仍在暴露窗口中。

### 方案 C — 两段式：先止血，再扩面（推荐）

先做 **Phase A：Layer B 关键完成链路排查与修补设计**，确认结果报告模板、飞书完成通知、Layer B hook / stop review 的责任边界；再做 **Phase B：扩展到 Layer A / Prism / 宿主覆盖率** 的系统性排查。

**优点**
- 先解决当前最痛的问题，同时保留“由此及彼”的扩展能力。
- 更容易把“主链故障”与“旁路漂移”分层描述清楚。

**缺点**
- 需要明确 Phase A / Phase B 的交接边界，避免中途又滑回“大而全”。

**推荐理由**

当前最危险的不是“问题多”，而是**责任边界不清**：模板、飞书、hook、stop review、宿主注册到底谁负责，已经出现语义混叠。方案 C 先把主链钉死，再做全面扩展，能最快降低风险且保留系统性视角。

## 4. 设计：调查框架

### 4.1 核心原则

本次调查不按“文件类型”拆，而按**不变量**拆。每个不变量都要回答五个问题：

1. **契约来源**：哪份文档规定了它必须发生？
2. **主触发链**：理论上应该由哪个流程或脚本触发？
3. **兜底链**：主触发缺失时，谁负责发现并补救？
4. **运行证据**：当前仓库里有哪些配置、脚本、标记文件、报告能证明它真的生效？
5. **失效后果**：如果它不发生，会静默损失什么？

### 4.2 本次要追的 5 个不变量

1. **完成报告模板不可漂移**
   - Layer B 自身开发任务完成后，必须按 `references/task-report-template.md` 回报。
   - 要查：模板契约是否只停留在文档；是否存在任何机器检查或 stop-hook 审计。

2. **飞书完成通知不可遗漏**
   - 要区分 Layer B 主链“流程内必须执行”与宿主 Hook 兜底“自动补发”。
   - 要查：Claude / Gemini / Copilot 三条链路分别由谁触发、谁兜底、现在有没有覆盖空洞。

3. **Layer B 独立评审不可被跳过**
   - 由 `redcap-on-stop-review.sh` + 宿主 stop/session-end 触发。
   - 要查：各宿主是否真的都能把 Layer B 收尾导向该脚本。

4. **文档宣称的宿主 Hook 覆盖率必须与实际注册一致**
   - 尤其是 Copilot `.github/hooks/`、Gemini `SessionEnd`、Claude `Stop`。
   - 要查：文档是“能力存在”还是“已部署”，当前仓库处于哪一档。

5. **主链失效时必须有可观察的补救痕迹**
   - 要查：是否有 marker file、review result、feishu record、report path、stderr/warn 等证据。
   - 如果完全无痕，就说明兜底机制不可观测，不可依赖。

### 4.3 调查矩阵（单一信源）

本次排查的核心产物不是“零散发现列表”，而是一张 **Hook / 收尾责任矩阵**：

| 维度 | 含义 |
|------|------|
| 层级 | Layer A / Layer B / Prism |
| 宿主 | Claude / Gemini / Copilot / Kimi |
| 事件 | InstructionsLoaded / Stop / SessionEnd / on_ALL_DONE / 手工流程步骤 |
| 契约来源 | CONTRIBUTING / SKILL / host-reliability / hook-standards / task-report-template |
| 实际注册 | `.claude/settings.json` / `.gemini/settings.json` / `.github/hooks/` / 无 |
| 实际脚本 | 哪个脚本真正处理 |
| 保障对象 | 模板 / 飞书 / 评审 / 清理 / pending_actions / archive |
| 主链/兜底 | primary / fallback / audit |
| 当前状态 | 已覆盖 / 漂移 / 未实现 / 文档过度承诺 |

这张矩阵将成为后续修复设计的单一信源。

## 5. 分阶段执行设计

### Phase A — 关键完成链路止血

目标：优先回答“为什么这次模板没走、飞书没发”。

**检查面**
- `references/task-report-template.md` 的消费链
- `CONTRIBUTING.md §5` 的 Layer B 飞书主链
- `.claude/settings.json` → 修复前 Stop 链快照（`redcap-claude-hook-stop.sh` / `redcap-on-stop-review.sh`）
- `.gemini/settings.json` → 修复前 SessionEnd 分发链快照（`redcap-layerA-session-end.sh` → Layer B 分发）
- 最近两次本地提交对应的真实完成路径（`aaa4882` / `6fa1591`）

**预期输出**
- 这两个现象分别属于：主链漏调 / Hook 漏触发 / 兜底失效 / 契约不存在 / 文档误导 的哪一种。

### Phase B — 全链路扩展排查

目标：由当前故障反推出相邻隐患，而不是止于两个表面症状。

**扩展面**
- Copilot hook 覆盖率与仓库现实是否一致
- Layer A 通用 SessionEnd 分发器是否真的同时满足 Layer A / Layer B 契约
- Prism 报告/归档/完成通知路径是否复用了相同失效模式
- “模板 / 通知 / review / cleanup” 四类不变量是否在所有宿主上都有主链与兜底

**预期输出**
- 一份按严重级别排序的隐患清单：P0（误导性承诺 / 静默失败）→ P1（兜底缺口）→ P2（文档与实现轻度漂移）。

## 6. 错误处理与边界

### 6.1 这次不做的事

- 不直接重构全部 hook 体系。
- 不把“能力存在”自动等同于“已部署”。
- 不把所有文档落差都升级为代码问题；会明确区分：
  1. 文档承诺错误
  2. 配置未部署
  3. 脚本逻辑缺陷
  4. 运行时宿主限制

### 6.2 发现 P0 时的处理原则

若发现以下任一情况，应直接进入后续实现优先级最高序列：

1. 文档宣称“有 Hook / 有兜底”，实际未注册或未实现。
2. 主链失效后，兜底链也不会留下任何可观察痕迹。
3. 不同宿主对同一不变量存在相反语义（例如一个宿主走 Layer B 直连，一个宿主误接到 Layer A 代理，且行为不同）。

## 7. 验收标准

本设计对应的调查完成后，必须能回答以下问题：

1. **结果报告模板为什么会被绕过？**
2. **飞书通知为何缺失：主链漏调、Hook 漏触发，还是兜底未实现？**
3. **Copilot / Gemini / Claude 当前各自到底覆盖了哪些 Layer B 收尾责任？**
4. **文档里还有哪些“写了但没部署 / 写了但不再真实”的承诺？**
5. **哪些隐患需要立即修，哪些只需下调文档口径？**

如果调查结束仍答不出这 5 个问题，则说明设计不合格，需要继续补充矩阵而不是贸然修代码。

---

## 8. 测试与验证设计

后续实现阶段不靠“看起来对”，而靠三类证据：

1. **静态证据**
   - 配置文件是否注册
   - 脚本是否被真实引用
   - 模板/文档是否有消费点

2. **运行证据**
   - 真实 hook 触发痕迹（stderr / marker file / record / log）
   - 是否产生飞书记录
   - 是否产出符合模板的报告

3. **故障注入证据**
   - 主链故意不执行时，兜底是否补发 / 告警 / 失败
   - 旧报告 / 错 run_id / 缺配置 / 缺模板消费时，是否被挡下而不是静默通过

---

## 9. 推荐的下一步

在获得用户确认后，按以下顺序实施：

1. 建立 Hook / 收尾责任矩阵（Phase A → Phase B）。
2. 先复盘最近两次实际完成路径（`aaa4882`、`6fa1591`）。
3. 对模板、飞书、Layer B stop review、Copilot hook 覆盖率分别给出 P0/P1/P2 结论。
4. 仅在根因清晰后再做代码修复和文档修正，避免“看到缺通知就补一个 notify”式头痛医头。
