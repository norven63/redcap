# 飞书双向交流与最小待处理入口设计

> 状态：已完成设计讨论，待实现
> 日期：2026-04-15
> 主题：把 RedCap 的飞书链路从“多维表格折中方案”升级为“固定单聊 + bot 发送 + 窗口式接收 + 最小待处理入口”，同时保持 CLI 为唯一主控制面。

---

## 1. 背景与问题

当前 RedCap 已有飞书能力，但主要依赖 webhook + 多维表格记录 + 轮询表格回复的方式来实现通知与问答。这个方案在“能用”层面成立过，但用户已经明确指出它存在三个根本问题：

1. **人类交互成本高**：需要建表、进表、编辑表，不符合自然沟通习惯。
2. **收尾通知真实可达性不稳定**：最近几次任务完成没有真正把通知送达用户可接收的飞书通道，说明“有配置”不等于“消息已达”。
3. **CLI 与飞书的控制权边界尚未设计清楚**：如果未来允许用户在飞书直接回复，就必须先说明它与 CLI 控制台如何兼容，不能让飞书桥变成第二个偷偷开工的前端。

与此相对，`/Users/norven/workspace/AI Era/feishu_cli_demo/` 已经提供了一条真实可达的路径：

- 使用 `lark-cli`
- 使用已验证 bot/profile
- 使用固定单聊 chat

因此，本设计不是抽象讨论“飞书能不能用”，而是要把 RedCap 的飞书能力迁移到一条**用户已经实际收到过消息**的 bot 通道上，并在此基础上补出最小可用的双向交流能力。

---

## 2. 目标与非目标

### 2.1 目标

本设计要完成五件事：

1. 将 RedCap 的**发送通知链**统一迁移到 demo 同款的 `lark-cli + bot + 固定单聊` 路径。
2. 建立一条**半实时的飞书回复接入链**：不做常驻监听，但在明确窗口内可轮询读取用户回复。
3. 让飞书与 CLI 的关系明确为：**CLI 是主控制面，飞书是备用输入输出通道**。
4. 为“窗口外飞书消息”提供一个**最小可用待处理入口**，支持记录、提醒、提取和删除。
5. 把失败语义补成诚实降级：发送失败、轮询失败、歧义回复、控制权冲突都不能伪装成成功。

### 2.2 非目标

本设计明确不做以下事情：

1. **不做原生 IM 客户端式实时聊天**。不追求毫秒级或秒级常驻连接。
2. **不引入公网事件订阅基础设施**。不要求这一刀就搭建 webhook 回调服务、隧道或公网入口。
3. **不把待处理入口膨胀成第二套 backlog 或第二套 `.dev-task.md`**。
4. **不允许飞书桥独立拥有执行权**。所有执行推进仍必须回到 RedCap canonical control plane。

---

## 3. 方案对比与最终选择

讨论阶段考虑了三种路线：

### 方案 A：继续沿用多维表格交互，只修收尾通知

- **优点**：改动最小，现有实现复用最多。
- **缺点**：人类使用成本高，用户已经明确认为这种模式低效；也无法自然满足“直接在飞书里回复”的预期。

### 方案 B：直接切到 bot 单聊 + 窗口式轮询接收 + 最小待处理入口（采纳）

- **优点**：
  - 发送链走用户已验证可达的通道；
  - 可以做到半实时的飞书回复；
  - 不需要常驻监听，也不需要公网事件回调；
  - 容易把 CLI / 飞书的控制权边界讲清楚。
- **缺点**：
  - 需要新设计窗口租约、消息去重、补扫历史与待处理入口。

### 方案 C：一步到位做事件订阅 / 实时驱动的聊天桥

- **优点**：体验最接近原生 IM。
- **缺点**：
  - 需要额外基础设施；
  - 当前 `lark-cli` 不提供现成的 IM 长连接监听模式；
  - 本轮复杂度明显高于用户要求的“半实时足够”。

### 最终决策

采纳 **方案 B**。  
理由是：它同时满足“消息真实可达”“允许飞书直接回复”“不常驻占资源”“不引入额外基础设施”这四个核心约束，而且最符合用户当前明确认可的交互边界。

---

## 4. 设计原则

本设计遵循以下不变量：

1. **CLI 始终是主控制面**。飞书桥不允许成为第二个独立大脑。
2. **同一时刻只允许一个有效执行者**。飞书只负责输送输入输出，不负责直接抢执行权。
3. **没有常驻监听**。只有窗口监听 + 后续补扫历史。
4. **所有输入先落状态，再决定是否继续执行**。
5. **CLI 优先级高于飞书**。只要 CLI 和飞书输入冲突，立即以 CLI 本地状态为准。

---

## 5. 总体架构

本设计将飞书能力拆成四个部件：

### 5.1 飞书发送适配层

负责把 RedCap 现有的“完成通知 / 提醒 / 回复确认”统一改成 demo 同款的 bot 发送通道：

- `lark-cli`
- 固定 profile
- 固定单聊 chat
- bot 身份

它只负责“发出去”，不负责接收、不负责执行判断。

### 5.2 飞书接收桥

负责在**有效窗口**里轮询固定单聊：

- 前 1 分钟每 10 秒一次
- 之后每 1 分钟一次

它只负责：

1. 读取消息历史
2. 找出新的用户回复
3. 交给窗口控制器判断

它不直接让 RedCap 跑起来。

### 5.3 窗口控制器

负责管理两种窗口：

1. **等待答复窗口**：当前任务真的在等用户回答，CLI 对应 `need_user / blocked / paused` 等等待态。
2. **任务完成回访窗口**：当前任务已收尾，但给用户保留一个短时 follow-up 入口，例如允许直接回“继续下一步”。

窗口控制器负责：

- 创建窗口租约
- 关闭窗口
- 覆盖旧窗口
- 判定飞书回复是否命中当前窗口
- 判定是否允许自动恢复执行

### 5.4 最小待处理入口

负责承接**补扫历史**时发现的“窗口外飞书消息”。  
这一层只做最小能力：

- 记录
- 提醒
- 提取
- 删除 / 归档

它不是第二套 backlog，也不是第二套 `.dev-task.md`。

## 6. 窗口模型与执行权模型

## 6.1 双窗口模型

### 等待答复窗口

使用场景：

- RedCap 明确需要用户回答问题
- 当前任务不能继续推进

CLI 现象：

- 当前任务处于等待态
- RedCap 没有继续往下执行

### 任务完成回访窗口

使用场景：

- 当前任务已经完成
- RedCap 已发出任务完成通知
- 用户可能直接从飞书回复“继续下一步”或“这里再补一刀”

CLI 现象：

- 当前任务不是 blocking
- CLI 处在上一轮任务结束后的 idle / short follow-up 状态

## 6.2 执行权模型

1. **CLI 输入优先**：如果用户先回到 CLI 回复，则当前飞书窗口立即作废。
2. **飞书回复必须命中有效窗口**：只有命中窗口的回复才有资格继续后续判断。
3. **窗口外飞书消息不会直接抢执行权**：它们只会在后续补扫历史时进入待处理入口。
4. **自动恢复执行的范围受限**：
   - 只允许在 `等待答复窗口` 与 `任务完成回访窗口` 中自动恢复；
   - 窗口外消息不自动恢复；
   - 任何冲突优先退回 CLI 主控制面。

## 7. 消息流转

### 7.1 发送一条飞书消息时

当 RedCap 发出一条需要后续接收回复的飞书消息时，系统需要同时创建一个窗口租约，至少记录：

- `session_handle`
- `task_id`
- `window_type`
- `chat_id`
- `anchor_message_id`
- `opened_at`
- `poll_stage`
- `expires_at`

### 7.2 窗口存活期间

飞书接收桥按窗口租约中的策略轮询固定单聊。  
当读到新的用户消息时：

1. 先判断是否为当前窗口之后的新消息；
2. 再判断是否命中当前窗口；
3. 再写入本地 inbox / 状态；
4. 最后决定是否恢复执行。

### 7.3 命中有效回复时

处理顺序必须固定为：

1. 写状态
2. 关窗口
3. 发飞书确认
4. 恢复执行（若允许）

确认消息示例：

- “已收到，正在继续处理”
- “已收到，已记为待处理”

### 7.4 窗口关闭条件

窗口在以下四种情况之一发生时立即关闭：

1. 收到有效回复
2. 超时
3. CLI 先收到用户回复
4. 被新窗口覆盖

### 7.5 补扫历史

由于本设计不做常驻监听，因此“窗口外飞书消息”不可能被实时发现。  
它们的发现方式是：**后续在合适时机重新读取固定单聊历史，并找出在无有效窗口时期发出的新消息。**

补扫建议触发时机：

1. 下一次开窗时
2. 下一次 session-start 时
3. 下一次发送飞书通知前

补扫出来的窗口外消息统一进入待处理入口，不直接恢复执行。

## 8. 本地状态与最小待处理入口

## 8.1 本地状态文件

为了避免把瞬时飞书状态写进 repo-tracked canonical truth，本设计建议使用 local-only runtime 载体，例如放到 `compass/.workflow/` 下：

- `compass/.workflow/feishu-active-window.json`
- `compass/.workflow/feishu-chat-cursor.json`
- `compass/.workflow/feishu-pending.jsonl`

这三类文件的语义分别是：

1. **active-window**：当前有效窗口租约
2. **chat-cursor**：最近一次消费到的飞书消息位置
3. **pending**：待处理入口中的消息项

这些载体属于 local runtime / continuity 资产，不是 repo-tracked frozen evidence。

## 8.2 最小待处理入口的数据结构

每条待处理项最少要有：

- `pending_id`
- `source = feishu`
- `chat_id`
- `message_id`
- `raw_text`
- `summary`
- `created_at`
- `status`

建议状态最小集：

- `open`
- `promoted`
- `dismissed`

## 8.3 最小待处理入口的行为

### 记录

补扫历史发现窗口外消息时，生成一条待处理项。

### 提醒

提醒节点建议控制在低频但稳定的时刻：

1. 下一次任务完成时
2. 下一次 session-start 时
3. RedCap 准备开始新任务前

提醒话术要明确：

- “还有 N 条待处理”
- “要不要拿出来讨论实现细节和制定落地计划”

### 提取

当用户明确说“把待处理拿出来聊”时，待处理项才会被提升成正式讨论对象，并重新走 PM Gate / 设计 / 计划 / 实施流程。

### 删除 / 归档

当用户明确说“这条不用了 / 取消 / 没意义”时，待处理项转为 `dismissed`。  
当待处理项已经被正式吸收到新任务中时，转为 `promoted`。

## 9. 失败处理与诚实降级

### 9.1 发送失败

`lark-cli` 发送失败时，不允许伪装成“已通知”。  
必须显式记录：

- 发送失败事实
- 当前任务状态
- 是否保留重试机会

### 9.2 轮询失败

轮询失败时：

- 不自动恢复执行
- 不制造“已收到回复”的假象
- 在窗口仍有效时可继续保留窗口
- 达到阈值后显式降级

### 9.3 歧义回复

如果无法可靠判断一条飞书消息到底是：

- 当前窗口的直接答复
- 还是新的 follow-up

则默认降级到待处理入口，不自动恢复执行。

### 9.4 控制权冲突

只要 CLI 本地状态与飞书桥状态不一致，立即以 CLI 本地状态为准，关闭旧窗口，放弃旧桥的自动恢复资格。

## 10. 验证策略

实现完成后，至少需要覆盖以下验证：

1. **真实发送验证**：bot 通道能够把任务完成通知送达固定单聊。
2. **窗口接收验证**：有效窗口内的用户回复能够被识别、写入状态并关闭窗口。
3. **CLI 优先验证**：CLI 先回复时，飞书迟到消息不会误触发。
4. **补扫验证**：无窗口期间发出的飞书消息会在后续补扫中进入待处理入口。
5. **歧义降级验证**：不明确的飞书消息只会进待处理，不会误开跑。
6. **失败诚实验证**：发送失败、轮询失败、窗口冲突不会被伪装成成功。

## 11. 落地边界

本设计优先改造以下现有控制路径：

1. `compass/tools/feishu-notifier.py`
2. `compass/tools/redcap-on-complete.sh`
3. `compass/tools/redcap-layerB-session-end.sh`

其中：

- 发送链将迁移到 demo 同款 bot 通道；
- 接收链将新增窗口式轮询与补扫逻辑；
- 任务完成通知、等待答复与待处理提醒将统一接入这条新链。

---

## 12. 最终结论

本设计的核心不是“让飞书也能聊天”，而是：

1. 把通知链切回**真实可达**的 bot 通道；
2. 在不做常驻监听的前提下，补出**半实时、可控、不会与 CLI 打架**的飞书回复能力；
3. 顺手建立一个**最小可用待处理入口**，承接那些没有命中有效窗口、但也不该被静默丢掉的飞书 follow-up。

只要守住“CLI 是主控制面、飞书只是输入输出桥、窗口外消息靠补扫历史进入待处理入口”这三个边界，这条能力链就能一步到位地取代多维表格折中方案，而不会把 RedCap 变成两套前端互相打架的系统。
