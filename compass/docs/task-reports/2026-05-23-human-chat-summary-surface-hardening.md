## 一、需求背景

### 1.1 原始问题（用户原文，禁止改写）

> “我不要你用AI工作流门禁的方式汇报，这个要求难道没写进工作流门禁中么？”

> “那接下来你和棱镜是不是应该修复这个问题？”

### 1.2 触发背景

RedCap 已经对飞书通知和部分 CLI 首屏做过人类可读优化，但聊天回复这个最常见的出口没有被同等约束。这导致 Cap 可以在聊天主叙事中继续堆内部术语，让 Norven 难以判断真实进度。

### 1.3 原始意图覆盖审计

| 项 | 结论 |
|---|---|
| scope_status | full-for-this-defect |
| 原始意图 | 聊天汇报也必须讲人话，不能继续把内部工作流术语当正文主线。 |
| 已覆盖 | 已新增 `redcap summary`，并把 `assistant chat reply` 与 `bin/redcap summary` 纳入自动检查。 |
| 未覆盖/延期 | 正式发布、历史资产迁移、飞书实时回复监听不属于本轮。 |
| 用户可见边界 | 可以说“聊天汇报出口已纳入可回归检查”；不能说“所有沟通质量问题已永久根治”。 |

## 二、方案讨论

### 2.1 问题分析

这不是单纯“下次我注意措辞”的问题。只要没有一个可执行出口和检查器，长任务中仍会退化回术语堆砌。因此本轮把聊天汇报变成可运行、可检查、可复验的产品面，而不是继续依赖口头提醒。

### 2.2 方案选项

| 选项 | 描述 | 结论 |
|---|---|---|
| A | 只提醒 Cap 以后注意措辞 | 不采纳，无法回归 |
| B | 新增聊天摘要命令，并把它纳入人类可读检查 | 采纳 |
| C | 删除机器审计字段，避免术语泄漏 | 不采纳，会破坏自检能力 |

### 2.3 决策结果

| Q | 采纳方案 | 决策理由 | 决策方 |
|---|---|---|---|
| Q1 | B：摘要出口 + 检查器 | 同时降低用户阅读成本，并保留机器审计能力。 | CAP_DECIDE + Prism REVIEW |

## 三、落地结果

### 3.1 本轮完成了什么

本轮新增了 `redcap summary` 命令，让聊天汇报可以直接生成五段式摘要：完成了什么、效果、任务全景、下一步、是否需要 Norven。检查器会验证这个摘要不出现本轮禁止的内部术语。

### 3.2 解决后的效果

- Cap 后续汇报有了一个可调用的标准出口，不再只能凭记忆组织语言。
- 聊天摘要被纳入自动检查；如果内部术语再次泄漏，回归会失败。
- 机器审计信息仍保留在结构化输出里，RedCap 自检能力没有被削弱。
- Claude Code 首轮指出的“收口”和“带来的效果”问题已修正，并由 Claude Code / Kimi 复验通过。

### 3.2.1 术语对照（按文件/功能解释）

| 文件/功能 | 术语 | 人话解释 |
|---|---|---|
| `redcap summary` | 聊天摘要出口 | 给 Cap 直接复用的五段式人类汇报。 |
| `assistant chat reply` | 聊天回复 | 你在 Codex 窗口里直接看到的文字回复。 |
| `human product surface` | 人类产品面 | 人会直接阅读和使用的输出界面。 |
| machine audit fields | 机器审计字段 | 给脚本自检用的数据，不应该默认堆给人看。 |
